# OCI Landing Zone Reference Implementation Constitution

This project MUST turn configurations generated by
[OCI Landing Zone Operating Entities / Landing Zone Studio](https://oci-landing-zones.github.io/oci-landing-zone-operating-entities/)
into a deployed OCI foundation organized by the repeatable operations and independent
stacks defined in the
[Operations Advisory Landing Zone Repository Design](https://github.com/oracle-devrel/technology-engineering/tree/OperationsAdvisory-repository-design/oci-and-db/foundation/operations-advisory/multi-cloud-operating-models/landing-zone-repository-design).
It MUST then publish a reviewed project-foundation handoff consumable by the
[Multi-Cloud Control Plane (MCCP)](https://github.com/oracle-devrel/technology-engineering/tree/main/oci-and-db/foundation/operations-advisory/multi-cloud-operating-models/multi-cloud-control-plane)
so Project Teams can request governed Day 1 and Day 2 changes inside their assigned
boundary. The required delivery path is **Operating Entities/Studio generation ->
reviewed multi-stack foundation deployment -> MCCP project handoff**.

## Core Principles

### I. Operating Entities Generation

Foundation configuration files MUST be generated using the official Operating
Entities blueprint libraries, either through a supported Studio export or the
canonical Jsonnet model calling the same pinned libraries. This reference MUST
import, verify, and project that generated design into operation-owned configuration
sets. Resource semantics MUST remain upstream-owned, and accepted configuration and
dependency families MUST match the pinned Orchestrator facade. Generation and import
MUST validate supported scope, ownership, regions, and dependencies; Studio imports
MUST preserve supported source choices, report projection adjustments, and reject
unsupported designs explicitly. Upstream pin or adapter changes MUST update contract
tests and documentation. Reusing one generator prevents competing resource definitions.

### II. Operations-Based Multi-Stack Deployment

The project MUST support foundation deployment and lifecycle changes following the
Repository Design's repeatable OP00–OP04 operations. Stack boundaries MUST follow
operation ownership, environments, platforms, and regions, with explicit configuration,
state, dependencies, and review boundaries. Every resource MUST have one owning stack
state. OP00 MUST own consolidated IAM and non-regional global governance, managed from
the home region. Regional OP01, OP02, and OP03 stacks MUST remain independent and own
their network, security, and observability resources, with state stored in the managed
region. Hub bootstrap and completion MUST update the same OP01 state. OP04 MUST update
the existing OP00 IAM state and publish a handoff without creating another IAM or
handoff state. Dependencies MUST reject conflicting producers and cross-region
resource bindings. Each reviewed execution MUST target one selected stack through
the pinned Orchestrator using Terraform CLI or Oracle Resource Manager, without
cascading applies. Repository and execution-identity boundaries MUST match independent
writers. This limits state locking and the impact of changes to their owning boundary.

### III. MCCP Handoff and Project Independence

The project MUST provide the OP04 onboarding and handoff capability that connects
the deployed foundation to MCCP. Cloud Operations MUST verify that the assigned
resources and permissions exist before publishing the handoff. The package MUST
reuse MCCP's pinned TBAC contract and canonical schema-3 renderer, supply both machine
JSON and human Markdown, and identify the assigned compartments, network, environment,
region, repository routing, reviewed producer outputs, and actual catalog state owners.
It MUST pass the consumer gate for the selected foundation and retain genuine protected
workflow provenance. Project Teams MUST operate through their separate production and
non-production repositories and workload states, using MCCP's governed Day 1 and Day 2
request flow inside the published boundary. They MUST NOT acquire foundation executor
privileges or ownership of global IAM or shared networking. Project-owned NSG seeds
MUST remain separate from foundation-owned resources. The handoff makes foundation
ownership and project self-service independently governable.

### IV. Minimal Local Automation

The existing `reference.py`, `runtime.py`, and `onboard.py` helpers MUST remain the
default paths for their generation, preparation, and synchronization contracts.
New automation MUST address repeated or error-prone work and MUST NOT duplicate
upstream rendering, HCL, or runtime staging. Repository and runner setup, bucket
settings, saved-plan review, live verification, and output or handoff publication
remain explicit operator steps unless repetition justifies maintained automation.
Private workflows MAY orchestrate these steps but MUST preserve review and
provenance. This keeps the reference small enough to maintain against upstream.

### V. Evidence-Based Verification

Meaningful changes MUST state intent, contracts, boundaries, and acceptance
criteria before implementation, then record evidence against those criteria.
Adapter, operation, and runtime contract changes MUST update the relevant tests
and documentation. Before publication, contributors MUST run the unit suite,
generation, catalog validation, upstream family contract check, and documentation
link check. Offline checks MUST be described as offline evidence; claims about
Terraform plan/apply, live isolation, firewall behavior, or migration require
separate evidence from an approved OCI test installation.

## Implementation Boundaries

Reference source, tests, and synthetic examples MUST stay separate from customer
configuration and runtime outputs. Credentials, real installation OCIDs, states,
plans, and handoffs MUST NOT be committed. Public CI MUST be credential-free.
Privileged jobs belong only in a private, protected customer installation with
separate identities and approval gates. Repository development MUST NOT run OCI
deployment, Terraform apply, ORM jobs, or state migration unless explicitly
requested for a test installation. Existing installations MUST follow the
documented migration procedure when state boundaries or handoff formats change.

## Development and Review Workflow

Changes MUST be made on a branch and reviewed. For meaningful changes, contributors
MUST write a concise spec, then a plan, implement the change, and record acceptance
evidence. The spec-driven practice adds no deployment-path tool or framework.
Documentation MUST remain with its owning topic: setup in `docs/getting-started.md`,
workflow installation and variables in `docs/private-workflows.md`, and execution
or publication in the existing operation guides. Reviewers MUST check ownership,
region and state boundaries, upstream contract alignment, data separation, and
the stated acceptance evidence. The authoring tool MUST NOT run in the deployment
path.

## Governance

This constitution governs repository changes alongside the contributor contract
in `AGENTS.md`. Amendments MUST be proposed in a branch, explain the affected
principles and operational impact, and receive review before adoption. A change
that alters an operation or consumer contract MUST include a migration or
compatibility plan where existing installations can be affected. The amendment
MUST update the version and last-amended date. MAJOR versions remove or redefine
an existing obligation incompatibly; MINOR versions add principles or materially
expand guidance; PATCH versions clarify wording without changing obligations.
Every change review MUST assess compliance with these principles. A proposed
exception MUST be resolved through a reviewed amendment before acceptance. Any
temporary Sync Impact Report MUST be removed before committing an amendment.
